# Best Park / PV7: first real Dynarmic Cocos initialization

Verified on Windows with the owner's unmodified original ARM32 `libgame.so`
after October 29 reference-game tracing. **This is a development probe, not
a playable PV7 wrapper or production Android compatibility module.**

## What was executed

Source: `src/pv7_cocos_firstcall.cpp`. The probe links the existing
`Arm32GuestImage` mapper/relocator to Dynarmic's A32 JIT and uses
engine-neutral guest memory and named SVC import boundaries. It does not
link or substitute any other game's Cocos library.

The native game image loads at a real guest-relative address, with its
330 external imports relocated. Seven STT_OBJECT imports use guest
data addresses, not executable syscall thunks. A mock JavaVM/JNIEnv
invocation table stops at named unimplemented JNI slots rather than
dispatching through null pointers.

The smoke-only guest service layer currently includes:

- Bounded guest memory allocation, basic `malloc/calloc/realloc/free`,
  `posix_memalign` and C++ new/delete entry points.
- Guest-address memory and string operations with range checks.
- Android log calls, `__cxa_atexit` destructor registration, and selected
  single-byte C locale classifications.
- ARM Linux kuser TLS, memory barrier, and 32-bit CAS helper paths.
- Guest-executed, ARM-state `pthread_once` calling the *actual* guest
  initializer, plus single-threaded pthread key storage.
- Explicit import and JNI SVC traps that report guest PC, LR and raw
  argument registers. Unknown functionality halts safely.

The heap is a simple bump allocator without reusable frees, pthread
synchronization is **not** thread-safe, and the C locale/JNI/stdio
objects are diagnostic approximations. Their presence does not establish
production compatibility.

## Actual Best Park results

Windows MSVC release build compiled successfully using existing Dynarmic
and Boost sources from the owner's CNR checkout. The separate light build
lives on C: rather than duplicating the ~8,500-file repository onto
the nearly full D: drive.

`pv7-cocos-firstcall.exe libgame.so JNI_OnLoad`:

- Real guest `JNI_OnLoad` ARM Thumb code executes and logs "on load".
- Returns `0x00010004` (JNI 1.4).

`pv7-cocos-firstcall.exe libgame.so constructors`:

- Executes **all 324 native constructor entries** via Dynarmic, through
  the guest's own `pthread_once` initializer.
- Prints `ALL_CONSTRUCTORS_RETURNED count=324`.
- Exits 0 in the diagnostic configuration, with typed data imports.

`pv7-cocos-firstcall.exe libgame.so boot`:

- Executes all 324 constructors, then `JNI_OnLoad`, then the real
  `Java_org_cocos2dx_lib_Cocos2dxRenderer_nativeInit`.
- Game's own logs report "native init", "!getOpenGLView",
  "running shared application", and "end new AppDelegate".
- First unimplemented native service boundary is
  **`glCreateProgram`**, at the game's call site
  `LR=0x0121fca9` (guest base 0x01000000).
- Stops with `COCOS_NATIVE_INIT_STOP UNIMPLEMENTED_IMPORT:glCreateProgram`,
  process exit code 3 intentionally indicating unsupported service.
- Cocos initialization and rendering are **not** complete; no frame was
  generated by PV7.

On the owner's PC the tested executable and run log are preserved in:

`%LOCALAPPDATA%\PV7\CocosRuntimeProbe\pv7-cocos-firstcall.exe`

`%LOCALAPPDATA%\PV7\CocosRuntimeProbe\bestpark-boot-diagnostic.txt`

The original game library used for local tests stays in the separate
ARM32Classic reference folder. No game libraries, copyrighted assets,
raw trace data or proprietary file contents were committed.

## Next code work (prioritized)

1. Implement a real **OpenGL ES 2 dispatch bridge** associated with a
   valid host EGL context. `glCreateProgram` must call a real GLES
   implementation; returning made-up IDs is not sufficient.
2. Extend actual JNI env/class/activity methods and lifecycle dispatch
   beyond the fail-closed slot table. Reuse the wrapper's existing
   Android Java surface rather than replicating game behavior.
3. Route assets, OBB, data, cache, and file calls to the PV7 game's
   shared-storage redirection; preserve old path semantics.
4. Drive `nativeRender` after successful `nativeInit`; synchronize
   touches and render thread activity. Compare runtime traces to the
   confirmed original ARM32 level-1 trace.
5. Replace diagnostic heap, TLS, synchronization and locale approximations
   with durable production Bionic-compatible implementations.

## Reproduction

On the owner PC, with the owner's copy of `libgame.so`:

```powershell
$exe = "$env:LOCALAPPDATA\PV7\CocosRuntimeProbe\pv7-cocos-firstcall.exe"
$game = "$env:LOCALAPPDATA\PV7\ARM32Classic\reference-libgame.so"
& $exe $game constructors
& $exe $game JNI_OnLoad
& $exe $game boot
```

The main `pv7host`/CNR Unity runtime remains unchanged by this probe.
The Cocos target is development-only until a real GLES context, JNI
lifecycle, and functional rendering are tested inside the generated APK.
